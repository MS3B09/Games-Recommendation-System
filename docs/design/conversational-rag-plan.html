02 / The workflow

Four understandable steps.

  1. UnderstandRead this message and relevant chat history. Is it a title question, a factual question or a recommendation?
  2. RetrieveUse title aliases, keyword matches and MiniLM embeddings searched through pgvector.
  3. GroundAssemble a compact evidence packet. Apply explicit chat requirements when recommending.
  4. RespondGenerate natural prose. Validate selected IDs and show canonical catalog cards.

Offline: approved catalog → pinned game embeddings → database.
Online: chat request → query embedding → relevant evidence → model answer.

Chat remembers

Preferences the user states here, recent references, and chat-local played/disliked titles. “More like that” uses context. “Forget the budget” clears that requirement.

Chat does not import

Main favorites, My limits, feedback, saved lists or discovery history. Saving a chat card remains a bookmark action; it does not feed preferences back into the assistant.

Technical retrieval defaults
  • Exact/normalized names first; verified aliases next. Ambiguous franchises ask for clarification.
  • Up to 20 semantic + 20 actually matching keyword candidates.
  • Stable-ID merge using reciprocal rank fusion, initial constant 60 and equal channel weights.
  • At most eight evidence candidates and four displayed cards, within the existing 12,000-byte provider-input limit.
  • No universal similarity threshold is assumed; calibrate on development cases and freeze before evaluation.
  • Encoder failure falls back truthfully to title/keyword search, but does not satisfy the semantic-RAG completion gate.

Title lookup bypasses recommendation filters. The multiplayer preference remains available for the next recommendation.

An experience request

You

Find a relaxing single-player exploration game under $20.

Behind the answer

Check recorded price and single-player facts. Search by the meaning of “relaxing exploration.” Retrieve descriptions and explain supported matches without promising subjective enjoyment.

Embeddings find related meaning. Code checks hard requirements. The model turns evidence into a readable answer.

More conversation rules
  • “Would it meet those requirements?” evaluates the named game against prior conditions.
  • “I played it” excludes it from recommendations, not factual lookup; an unclear “it” asks for clarification.
  • “Include it again” can undo a chat exclusion. New chat clears chat memory.
  • Topic changes replace unrelated soft intent; uncertain hard-condition changes ask rather than silently relax.
  • A missing title means “not found in this catalog,” never “this game does not exist.”
  • Legacy stored criteria retain transcript/cards but need confirmation when their provenance is unknown.

04 / The technology choice

Lightweight LangChain.
Measured before adoption.

LangChain Core 1.7.0 is now pinned in serving. R0 demonstrated named-stage inspection, callbacks and replacement; R2 implements six finite stages through the existing metered provider. MiniLM creates embeddings and pgvector searches them. No agent loops, automatic retries or second provider client.

What we would use

  • Small Runnable stages and document adapters.
  • Our existing restricted database repository.
  • Our existing metered provider transport.
  • Local stage timings and reproducible tests.

What adoption must prove

  • Same results and provider-call counts as direct Python stages.
  • Added warm orchestration p95 ≤25 ms; added warm RSS ≤30 MiB.
  • Total representative API peak RSS below 400 MiB.
  • Concrete testing/composition benefit; measured dependency/startup costs.
Measured R0 results: 300 warm mocked turns per method; identical results/call counts; worst added p95 9.870 ms; added warm RSS 23.973 MiB; maximum representative API interpreter peak 259.625 MiB. All specified numeric gates pass. Costs: 13 added distributions and 2.39–7.69 seconds local import/build time. Read the measurements, limitations and configuration handoff. No agent loops, paid tracing or second unmetered provider client.

Known limits and rollback

A small catalog limits coverage. Embeddings are relevance signals, not fact guarantees. Natural prose still needs evaluation. Local CPU success is not proof of hosted performance; verify hosting allowances and resources before a separate deployment decision.

Prefer additive changes, compatible sessions and pinned artifacts. Test any necessary migrations locally first; remote database changes need authorization. Roll back the implementation slice/configuration without destroying sessions or resetting quotas. No paid service, model training or live scraping is required.
